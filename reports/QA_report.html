DEF-01Sev 2

A deduction larger than gross pay is accepted, and take-home pay goes negative

Steps
$800 gross. Benefits and Deductions → 401(k), Dollar amounts, $1,000 → Calculate.
Expected
Blocked or capped at the pay available. A percentage of 100 % or more is already blocked.
Actual
Accepted with no message. Take home pay −$261.20 (−32.65 %). Roth $1,000 → −$347.96; Medical $900 → −$100.00.
Why
A paycheck cannot be negative. Payroll engines reduce or defer deductions to keep net pay at zero or above (Check, PeopleSoft).
Fix
One net-pay floor in the calculation also fixes DEF-11.

DEF-05Sev 2

A wage typed with a decimal comma is multiplied by ten

Steps
Type 20,5 as the hourly wage (decimal comma, used across Europe and Latin America).
Expected
Read as 20.50, or rejected with a message.
Actual
The field shows 205.00 with no warning. Gross for 40 h $8,200.00 instead of $820.00.
Why
Comma decimals are a known input-localisation problem (W3C locale-based forms, Adobe number field).
Screen recording (also shows DEF-07 and DEF-04)
DEF-10Sev 2New

Percentage deductions are silently rounded to a whole percent

Steps
401(k), "% Percent of gross pay", type 4.5 → Calculate.
Expected
Pre-tax deduction $36.00 (4.5 % of $800), or a message that decimals are not allowed.
Actual
The box changes to 5. Pre-tax deducted $40.00, 11 % more than requested. Typing 99.99 is rounded to 100 and then rejected with "Must be less than 100", although the hint says "0 to 100".
Why
Fractional contribution rates are common, and the user is never told their number was changed (WCAG 3.3.4, financial data).
Screen recording
DEF-11Sev 2New

Extra federal or state withholding larger than gross is accepted, and take-home goes negative

Steps
$800 gross. W-4 line 4(c) extra withholding $5,000 → Calculate. Then clear it and set Alabama additional withholding $2,000 → Calculate.
Expected
Rejected, or withholding capped at the pay available.
Actual
Both accepted with no message. Take home −$4,315.28 (federal) and −$1,347.96 (state).
Why
Tax can only be withheld from wages actually paid. Same root cause as DEF-01, through different fields.

DEF-13Sev 3New

The calculation endpoint does not validate input on the server

Steps
Run a normal calculation, then send the page's own request again from inside the page with one field changed (same browser, cookies and bot clearance as the user).
Expected
A 4xx validation error for every invalid field. Never a computed paycheck, never a server error.
Actual
Wage −20 → HTTP 200, gross −$800. Wage abc or missing → 200, gross $0. 401(k) 150 % → 200, all zeros. Hours −40, 100,000 hours, or frequency Fortnightly → HTTP 500. Empty or malformed body → 400 and unknown state → 404 are correct.
Why
Browser checks can be bypassed; the server has to enforce them (OWASP secure coding, OWASP C5, CWE-602). A 500 for bad input also hides real outages in monitoring.
Scope
11 requests in total, functional checks only. No load, fuzzing or exploitation.

DEF-12Sev 3New

A pay date in 1899 is accepted, and the result is a silent $0.00

Steps
Pay date 01/15/1899 → Calculate.
Expected
The date field rejects a year with no tax tables, with a message.
Actual
No message, Calculate enabled. The server answers HTTP 200 with "grossPay":"0.00", and every row shows $0.00 with no error. A year of 2150 is calculated quietly with current tax tables.
Why
A $0.00 paycheck looks like an answer, not an error (WCAG 3.3.1 error identification). Impossible dates such as 30 Feb and month 13 are rejected correctly.

DEF-14Sev 3New

1.5 dependents is accepted, then silently treated as 0

Steps
Alabama "How many dependents" = 1.5 → Calculate. Compare with 0 and 1.
Expected
Whole numbers only, with a validation message.
Actual
Not flagged, HTTP 200. Alabama tax: 0 dependents $32.68, 1 dependent $31.72, 1.5 dependents $32.68. The value is dropped, so the employee is over-withheld, and nothing tells the user.

DEF-02Sev 3

Wage 1e308 passes validation, and the server returns invalid JSON

Steps
Type 1e308 as the hourly wage → Calculate.
Expected
An upper bound on the field with a validation message.
Actual
The field shows a 309-digit number and is not flagged. The server answers HTTP 200 with "grossPay":"Inf" and bare NaN. The page shows a generic "something went wrong on our end". The same parser reads 1e2 as $100 and 1e3 hours as 1,000.
Why
Infinity and NaN are not permitted in JSON (RFC 8259, ECMA-404).

DEF-04Sev 3

Hours are not limited to the length of the pay period

Steps
Weekly, 1,000 regular hours → Calculate. Repeat with other frequencies and with overtime.
Expected
Regular plus overtime hours cannot exceed the hours in the period (168 in a week).
Actual
Weekly 1,000 h → $20,000.00 for one week. Biweekly 337 h, Semi-monthly 400 h and Monthly 745 h are all accepted. Weekly 40 h + 150 h overtime → $5,300.00. At 100,000 h the server answers HTTP 500.

DEF-08Sev 3

An overtime rate below the regular rate is accepted

Steps
$20 regular. Add Overtime: $10 × 12 h → Calculate.
Expected
A warning: overtime must be at least 1.5 × the regular rate ($30).
Actual
Accepted silently, gross $920.00. The field's own hint says "Overtime is a higher hourly wage".
Why
FLSA overtime is at least one and one-half times the regular rate (29 CFR 778.107).

DEF-06Sev 3

The date hint says MM/DD/YYYY, but UK and India browsers get Day/Month/Year

Steps
Open the page with browser language en-GB or en-IN. Read the pay-date label and the field.
Expected
The hint matches the order of the field.
Actual
Label "(MM/DD/YYYY)", field 21 / 11 / 2026. A user following the hint types 11/12/2026 for 12 Nov and gets 11 Dec, which can change the tax year in December.
Why
A stated format must match the field (WCAG 3.3.2, technique G89).

DEF-09Sev 3

Accepting the cookie banner wipes everything typed

Steps
Fresh visit. Type wage $35, choose Weekly, then click "Accept all cookies".
Expected
The banner closes and the input stays.
Actual
The page reloads. Wage is empty and frequency is back to Bi-weekly.
Why
Users should not have to re-enter information in the same process (WCAG 2.2 3.3.7 Redundant Entry).

DEF-07Sev 4

The hourly-wage hint shows the overtime rule

Steps
Read the hint under "What is your employee's hourly wage?".
Expected
Text that describes the wage.
Actual
"Work more than 8 hours a workday or more than 40 hours per workweek." Screen readers announce it with the wage field and with its error.

Also checked

Verified correct on live
  • Gross = rate × hours to the cent (40.01 h, 0.001 h, 168 h)
  • Social Security and Medicare rounded separately; 2026 wage base $184,500 caps Social Security at $11,439.00 per check; 0.9 % Additional Medicare above $200k
  • A 2025 pay date uses the 2025 wage base
  • 401(k), Section 125, HSA and Roth tax treatment; Social Security and Medicare exemptions
  • Negative, zero and non-numeric wage and hours rejected; negative deductions, negative W-4 values and a $0 overtime rate rejected
  • 30 Feb and month 13 rejected; 29 Feb 2028 accepted
  • Script payloads in fields are not executed
  • Net + taxes + deductions = gross; the panel matches the server response; an error is shown when a request fails
  • axe-core WCAG 2.x A/AA scan of the form: no violations
  • 390 px phone width: no sideways scrolling; no touch target under 24 px
Observations for the product owner
  • A wage below the $7.25 federal minimum ($0.01/h) is accepted with no warning
  • 41 regular hours are paid at straight time with no overtime prompt
  • 3-decimal wages are rounded to cents silently (20.999 → 21.00)
  • No upper bound on wage ($999,999,999/h) or dependents (1,000). W-4 Step 3 accepts $2,001, which no W-4 produces ($2,200 per child, $500 per other dependent)
  • After calculating, changing an input leaves the old result on screen with no "out of date" cue
  • The pre-tax deduction and fringe-benefit rows use identical labels with no group legend, so screen-reader users cannot tell them apart
  • Percentages are formatted inconsistently (81.5 % next to 81.51 %)
  • The endpoint rate-limits after about 40 calculations; headless browsers get a Cloudflare challenge

Method and limits

How each finding was confirmed

  • Expected values come from an independent reference model in the repository, from the page's own hints, and from the cited rules. They are not copied from Gusto's output.
  • A defect is reported only after it reproduced in at least two separate runs and the server response was checked, not only the screen.
  • Five suspected "date" bugs and one percentage bug from a first draft turned out to be faults in my own test script. They were fixed and re-run before anything was reported.
  • Automated regression tests mark each known defect as an expected failure. When Gusto fixes it, the test turns red and tells us to update it.

Not covered yet

  • Logged-in Run payroll (cut-off times, PTO, bonus runs) and the Gusto API. These need a demo company, a saved login and an API token.
  • States other than Alabama.
  • Load, performance and security testing beyond input validation. The server-side checks were 11 paced requests.
